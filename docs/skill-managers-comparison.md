# AI エージェント・スキル管理ツール比較

## 調査範囲と読み方

対象は Rosie、Vercel の `skills` CLI、Microsoft APM（Agent Package Manager）、GitHub CLI の `gh skill` である。ここでいう「管理」は、スキルの探索・取得・配置・更新・追跡を指す。エージェントが取得後の指示をどう実行するかまでは各ツールの責任範囲に含まれない。

以下では、公式ドキュメントおよび公式リポジトリの実装を優先した。公式に明記された事項を「事実」、複数の事実を組み合わせた選定判断を「推論」と明示する。

### Vercel URL の訂正（重要）

`https://github.com/vercel-labs/skillsh` は GitHub の 404 であり、比較対象のリポジトリとしては扱わない（[404 の URL](https://github.com/vercel-labs/skillsh)）。本稿では、CLI の README、ソース、npm メタデータを持つ [vercel-labs/skills](https://github.com/vercel-labs/skills) を「おそらく意図された訂正先」として比較する。この訂正は確定した URL の同一性を意味しないため、表・本文では常に **Vercel `skills`（訂正候補）** と表記する。

## 各ツールの実装と限界

### 1. Rosie

**実装モデル（事実）**

- `rosie install owner/repo` は ref 解決、tarball download、展開、`SKILL.md` 探索、agent 検出、配置を行う。skill 探索は root、`skills/`、深さ 5 までの再帰の順である（[how it works](https://rosie.astro.build/docs/how-it-works/)、[discovery](https://rosie.astro.build/docs/discovery/)）。
- project install は `.agents/skills/<name>` を canonical copy とし、各 agent のディレクトリから symlink を張る。`--global` の GitHub source は各 `~/<agent>/skills` に copy され、ローカル source は symlink になる（[CLI](https://rosie.astro.build/docs/cli/)）。
- `.agents/rosie.lock` は name/source/ref/SHA/timestamp/pin-or-auto/kind を一行ずつ保存する。引数なし `rosie install` は lock の SHA を再インストールする（[lockfile](https://rosie.astro.build/docs/lockfile/)）。
- `--ref` は README 等を `.agents/references/<name>/REFERENCE.md` に置き、既存の AGENTS.md、CLAUDE.md、GEMINI.md、Copilot instructions の最初に見つかったファイルへ managed block を追記する。reference は project-only である（[references](https://rosie.astro.build/docs/references/)、[agents](https://rosie.astro.build/docs/agents/)）。
- private GitHub の認証は公式 source で `GH_TOKEN`、`GITHUB_TOKEN`、`gh auth token`。token は GitHub host（`github.com`／`api.github.com`／設定した GHES host）以外へ付けない（[HTTP source](https://github.com/withastro/rosie/blob/main/src/http.rs)）。
- security page は、skills/references の invisible Unicode 除去、reference の HTML/reference-link comment stripping、tag rewrite の検出、agent-context 時の audit 出力を明記する（[security](https://rosie.astro.build/docs/security/)）。

**限界（事実と推論）**

- global GitHub install は docs 上「no lockfile」。従ってチームで commit した project lock による global 環境の再現はできない（[CLI](https://rosie.astro.build/docs/cli/)）。これは personal global cache としては妥当だが、CI／fleet 管理には弱い（後半は推論）。
- tag rewrite は検出して高 severity audit に出すが、更新を自動拒否しない（[security](https://rosie.astro.build/docs/security/)）。人間／agent の確認を必須にする運用が必要（推論）。
- 公式 security page は sandbox、heuristic phrase scan、signed release、registry、reputation、allowlist を範囲外とする（[security](https://rosie.astro.build/docs/security/)）。高信頼環境では APM の policy／CI gate 等を併用する必要がある（推論）。
- Website の how-it-works は「単一 C program、libcurl/libarchive」と説明する一方、repository の v0.8.5 `Cargo.toml` は Rust crate と `ureq`／`rustls` を示す（[website architecture](https://rosie.astro.build/docs/how-it-works/)、[Cargo.toml](https://github.com/withastro/rosie/blob/main/Cargo.toml)）。これは docs と source の不一致であり、導入時に配布バイナリの実装を確認すべきである（推論）。

### 2. Vercel `skills`（訂正候補）

**実装モデル（事実）**

- `npx skills add` は GitHub shorthand、任意 Git URL、local、直接 download URL を扱う。直接 URL の既定上限は download 10 MiB、展開 25 MiB、archive 1000 files（[README: source formats](https://github.com/vercel-labs/skills/blob/main/README.md#source-formats)、[source parser](https://github.com/vercel-labs/skills/blob/main/src/source-parser.ts)）。
- project／global scope と agent-specific path を持ち、symlink（推奨）または copy を選べる（[README](https://github.com/vercel-labs/skills/blob/main/README.md#installation-methods)、[agents table](https://github.com/vercel-labs/skills/blob/main/README.md#supported-agents)）。
- `skills use` は一時ディレクトリへ解決済み skill を書き、prompt を stdout に出す。`--agent` を付けた場合は supported agent を起動するが、install 済み状態にはしない（[README](https://github.com/vercel-labs/skills/blob/main/README.md#use-a-skill-without-installing)）。
- project lock は `skills-lock.json`。version、source、source URL/type、ref、skill path、disk 内容から算出した SHA-256、provider digest 等を保持し、timestamp を意図的に入れない。global lock は `~/.agents/.skill-lock.json` で GitHub tree SHA を保持する（[local-lock.ts](https://github.com/vercel-labs/skills/blob/main/src/local-lock.ts)、[skill-lock.ts](https://github.com/vercel-labs/skills/blob/main/src/skill-lock.ts)）。
- update は GitHub tree API を匿名→明示 `GITHUB_TOKEN`／`GH_TOKEN`→`gh api` の順で利用し、API 不可時は authenticated Git clone に fallback する（[AGENTS.md](https://github.com/vercel-labs/skills/blob/main/AGENTS.md#update-checking-system)）。
- GitHub private source は既存 Git credential helper、GitHub CLI、SSH を利用し、Vercel CLI 自身は `gh auth token` の credential を Node process に取り出さない。`GITHUB_TOKEN`／`GH_TOKEN` は optional（[README: private repositories](https://github.com/vercel-labs/skills/blob/main/README.md#private-repositories)）。
- CLI は匿名 telemetry と audit endpoint（`https://add-skill.vercel.sh/t`／`/audit`）を使用する。audit lookup は timeout 3 秒、失敗時は `null` となり install を止めない。`DISABLE_TELEMETRY=1` または `DO_NOT_TRACK=1` で両方を止められる（[telemetry.ts](https://github.com/vercel-labs/skills/blob/main/src/telemetry.ts)、[README: telemetry](https://github.com/vercel-labs/skills/blob/main/README.md#telemetry)）。

**限界（事実と推論）**

- `skills-lock.json` は依存グラフを宣言する manifest ではない。README／source に transitive package dependency resolver の説明はなく、lock entry は skill 単位である（[local-lock.ts](https://github.com/vercel-labs/skills/blob/main/src/local-lock.ts)）。複数 skill 間の依存関係、policy inheritance、MCP の宣言は APM のようには扱えない（推論）。
- partner audit は表示用 advisory で、source code は network error／timeout を無視して install を続ける（[telemetry.ts](https://github.com/vercel-labs/skills/blob/main/src/telemetry.ts)）。安全判定が得られない場合も installation gate にはならない（事実からの直接的帰結）。
- telemetry は public GitHub と確認できた場合だけ repo／skill identifier を送るという README の方針だが、GitHub 以外は visibility を確認できず identifier が含まれ得る（[README: telemetry](https://github.com/vercel-labs/skills/blob/main/README.md#telemetry)）。組織のデータ送信ポリシーでは disable を標準化すべきである（推論）。
- skill metadata の注入・symlink/copy・path safety はあるが、APM のような lock replay を含む pre-deploy Unicode gate や org allowlist は README／実装の比較対象範囲にはない（[README](https://github.com/vercel-labs/skills/blob/main/README.md)、[add.ts](https://github.com/vercel-labs/skills/blob/main/src/add.ts)）。これは「機能が絶対にない」の主張ではなく、本調査で確認できた trust boundary の差分である。

### 3. Microsoft APM

**実装モデル（事実）**

- `apm.yml` が project package の manifest、`.apm/` が authoring source、`apm_modules/`・target directories・`apm.lock.yaml` が生成物である（[package anatomy](https://microsoft.github.io/apm/concepts/package-anatomy/)）。
- `dependencies.apm`／`devDependencies.apm` の package を recursive に解決し、MCP/LSP、scripts、target、marketplace／registry も扱える（[manifest schema](https://microsoft.github.io/apm/reference/manifest-schema/)、[manage dependencies](https://microsoft.github.io/apm/consumer/manage-dependencies/)）。
- `apm install` は resolve → policy gate → hidden Unicode scan → integrate → lockfile の順で動作し、critical finding は既定で block。`--force` は検査を bypass して上書きできる（[install](https://microsoft.github.io/apm/reference/cli/install/)、[install packages](https://microsoft.github.io/apm/consumer/install-packages/)）。
- `apm.lock.yaml` は full dependency graph、resolved commit、ref/version、SHA-256、deployed files、MCP/LSP 状態を記録する。`apm install --frozen` は lock と manifest の不一致／欠落時に書込み前に fail する（[lockfile spec](https://microsoft.github.io/apm/reference/lockfile-spec/)、[install](https://microsoft.github.io/apm/reference/cli/install/)）。
- `apm audit` は hidden Unicode、lock／target drift、canonical ownership を検査し、`--ci` で machine-readable／SARIF gate にできる（[audit](https://microsoft.github.io/apm/reference/cli/audit/)）。
- public GitHub は認証不要。private GitHub は `gh auth login`／`GITHUB_APM_PAT`、GitLab は `GITLAB_APM_PAT`、Azure DevOps は `ADO_APM_PAT`／`az login`、その他は Git credential helper／SSH（[authentication](https://microsoft.github.io/apm/consumer/authentication/)）。
- enterprise security model は、install 完了後の runtime process、phone-home telemetry、arbitrary code execution を既定では持たないと明記する。ただし opt-in lifecycle scripts／experimental executable surfaces は別 trust gate である（[security model](https://microsoft.github.io/apm/enterprise/security/)）。

**限界（事実と推論）**

- APM は単なる SKILL.md installer より manifest、resolver、compiler、policy、MCP integration が多く、導入・学習・CI 設定のコストが高い（機能面からの推論）。skill だけを個人で一つ入れる用途では Rosie／Vercel／gh の方が短い。
- manifest schema v0.3 と lockfile v0.2 は docs が Working Draft と明記する（[manifest schema](https://microsoft.github.io/apm/reference/manifest-schema/)、[lockfile spec](https://microsoft.github.io/apm/reference/lockfile-spec/)）。将来の仕様変更を前提に CLI version、lock、CI を同時更新する運用が必要である（推論）。
- security model は runtime sandbox、malware analysis、package signing を行わないと明記する（[security model](https://microsoft.github.io/apm/enterprise/security/)）。従って scan／hash／policy は強いが、取得後の MCP サーバーや agent の権限隔離までは代替しない。
- `--force` は critical scan block と locally-authored file collision を同時に越えられる強力な escape hatch である（[install](https://microsoft.github.io/apm/reference/cli/install/)）。CI では禁止または承認付きにするのが安全である（推論）。

### 4. GitHub CLI `gh skill`

**実装モデル（事実）**

- `gh skill install` は GitHub repo の skill を discovery し、選択した agent host の project/user path に copy する。default scope は project、non-interactive の default agent は GitHub Copilot（[install source](https://github.com/cli/cli/blob/trunk/pkg/cmd/skills/install/install.go)）。
- skill 名なしでは最新 tagged release、次に default branch HEAD を解決する。`skill@VERSION`／`--pin` は tag、branch、commit SHA に固定できる（[install source](https://github.com/cli/cli/blob/trunk/pkg/cmd/skills/install/install.go)）。
- `gh skill preview` は file tree と `SKILL.md` を pager に出し、追加ファイルも選択して閲覧できる。install 前 review のための機能である（[preview manual](https://cli.github.com/manual/gh_skill_preview)）。
- `gh skill update` は install metadata の GitHub tree SHA と remote SHA を比較する。pinned skill は skip、`--force` は local modification を上書きし得る。metadata がない skill は interactive で source repo を求め、non-interactive／`--all` では skip する（[update manual](https://cli.github.com/manual/gh_skill_update)）。
- global lock の version 3 は source、source URL/type、skill path、tree SHA、pin、installed／updated timestamps を JSON に保持する。file lock は `flock` で concurrent update を直列化する（[lockfile source](https://github.com/cli/cli/blob/trunk/internal/skills/lockfile/lockfile.go)）。
- publish は Agent Skills naming/frontmatter、directory name、`allowed-tools` type、install metadata 除去を検証し、GitHub topic と semver tag の release 作成を案内する（[publish manual](https://cli.github.com/manual/gh_skill_publish)）。

**限界（事実と推論）**

- `gh skill` は GitHub CLI に密結合し、remote source／search／publish は GitHub 前提である（[manual](https://cli.github.com/manual/gh_skill)、[search manual](https://cli.github.com/manual/gh_skill_search)）。GitLab、任意 Git host、marketplace、MCP、transitive dependency を一つの manifest で管理する用途には向かない（推論）。
- current installer の lock record は home 配下 `~/.agents/.skill-lock.json` に書くため、project scope に install しても APM の `apm.lock.yaml` や Vercel の `skills-lock.json` のような project manifest／lock replay にはならない（[lockfile source](https://github.com/cli/cli/blob/trunk/internal/skills/lockfile/lockfile.go)）。チームで同じ project state を再構築する場合は、pin と明示的な CI 手順を別途管理する必要がある（推論）。
- install source／installer は frontmatter、safe path、source metadata、tree hash を扱うが、APM の policy gate や Unicode pre-deploy scan は呼び出していない（[install source](https://github.com/cli/cli/blob/trunk/pkg/cmd/skills/install/install.go)、[installer](https://github.com/cli/cli/blob/trunk/internal/skills/installer/installer.go)）。これは実装を読んだ上での限定的な推論であり、GitHub repository 自体の安全性を保証しない。
- preview は review を助けるが、人間が preview せず `--all`／`--force` を使えば内容はそのまま agent context になる（[preview manual](https://cli.github.com/manual/gh_skill_preview)、[install source](https://github.com/cli/cli/blob/trunk/pkg/cmd/skills/install/install.go)）。

## 推奨構成

| 用途 | 第一候補 | 理由 | 注意 |
|---|---|---|---|
| 組織で複数 agent、MCP、instructions まで一元管理 | **APM** | manifest、transitive dependency、multi-target compile、lock、policy、audit CI が一つにある（[manifest](https://microsoft.github.io/apm/reference/manifest-schema/)、[security](https://microsoft.github.io/apm/enterprise/security/)）。 | Working Draft の schema。runtime sandbox／署名は別途必要（[manifest status](https://microsoft.github.io/apm/reference/manifest-schema/)、[security limitations](https://microsoft.github.io/apm/enterprise/security/)）。 |
| 軽量な project skill 導入、native binary、レビュー可能な SHA lock | **Rosie** | `.agents/rosie.lock`、project canonical copy、agent symlink、Unicode／tag rewrite audit（[lockfile](https://rosie.astro.build/docs/lockfile/)、[security](https://rosie.astro.build/docs/security/)）。 | global GitHub copy は project lock 外。signed release／allowlist／sandbox なし（[CLI](https://rosie.astro.build/docs/cli/)、[security](https://rosie.astro.build/docs/security/)）。 |
| 多数の agent と provider、簡単な `npx` 導入、skill を一時利用 | **Vercel `skills`（訂正候補）** | 73 agent、GitHub/GitLab/Git/local/archive、`skills use`、symlink/copy、local/global lock（[README](https://github.com/vercel-labs/skills/blob/main/README.md)）。 | telemetry/audit は外部 advisory、transitive dependency／org policy の代替ではない（[telemetry](https://github.com/vercel-labs/skills/blob/main/src/telemetry.ts)）。 |
| GitHub 中心の個人開発、既存 `gh auth`、publish まで GitHub 内で完結 | **`gh skill`** | GitHub CLI の auth、search、preview、install、update、publish を同じ操作面で使える（[gh skill](https://cli.github.com/manual/gh_skill)、[publish](https://cli.github.com/manual/gh_skill_publish)）。 | preview 段階。project lock replay、GitHub 外 source、依存 graph、Unicode／policy gate は期待しない（[gh skill status](https://cli.github.com/manual/gh_skill)）。 |
| 高リスク供給元を CI で拒否したい | **APM + `apm audit --ci`** | lock consistency、drift、hidden Unicode、policy を gate 化できる（[audit](https://microsoft.github.io/apm/reference/cli/audit/)、[security](https://microsoft.github.io/apm/enterprise/security/)）。 | signing／malware scan／runtime isolation は追加の security platform の責任（[security](https://microsoft.github.io/apm/enterprise/security/)）。 |

## 運用上の結論

1. **一つの project で manager を混在させない。** Rosie、Vercel、APM、gh はいずれも `.agents/skills/` または agent 固有 directory を書き得るため、同じ skill 名を複数 manager で管理すると canonical copy、symlink、lock の所有者が分裂する（各 tool の配置表からの推論）。project の所有者を一つ決め、他は preview／search に限定する。
2. **再現性が必要なら project lock を commit する。** Rosie は `.agents/rosie.lock`、Vercel は `skills-lock.json`、APM は `apm.yml` + `apm.lock.yaml` が該当する。一方 `gh skill` は current implementation の global lock を中心に動くため、`--pin`、source、skill path を CI 設定として明示する（[Rosie lock](https://rosie.astro.build/docs/lockfile/)、[Vercel local lock](https://github.com/vercel-labs/skills/blob/main/src/local-lock.ts)、[APM lock](https://microsoft.github.io/apm/reference/lockfile-spec/)、[gh lock](https://github.com/cli/cli/blob/trunk/internal/skills/lockfile/lockfile.go)）。
3. **security は内容の trust と runtime 権限を分ける。** Rosie／APM は hidden Unicode と provenance を扱い、Vercel／gh は discovery／metadata／path と preview を中心に扱う。しかし全ツールとも、取得した指示を読む agent や MCP の権限を完全に sandbox するものではない（[Rosie security](https://rosie.astro.build/docs/security/)、[APM security](https://microsoft.github.io/apm/enterprise/security/)、[Vercel telemetry/audit](https://github.com/vercel-labs/skills/blob/main/src/telemetry.ts)、[gh installer](https://github.com/cli/cli/blob/trunk/internal/skills/installer/installer.go)）。
4. **認証情報を lock／report に書かない。** GitHub token は環境変数または各 CLI credential store に置き、source URL や generated audit に token が混入しないことを確認する。Vercel README と source は GitHub CLI credential を Node process へ取り出さない設計、Rosie は token を GitHub host にだけ送る設計を明記している（[Vercel auth](https://github.com/vercel-labs/skills/blob/main/README.md#private-repositories)、[Rosie HTTP](https://github.com/withastro/rosie/blob/main/src/http.rs)）。
