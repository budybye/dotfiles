# TDD（テスト駆動開発）

t-wada（和田卓人）さんの考え方に基づく、テスト設計・実装の指針。目標は「動作するきれいなコード」。動作ときれいさを同時に追わず、順番に進める。

## 基本サイクル

1. **Red** — 新しい期待振る舞いか既存不具合を表す最小のテストを書く。新機能は未実装で、バグ修正は既存欠陥で失敗することを確認する。Characterization Testは現在の動作を記録するため、通過してよい。
2. **Green** — テストを通すために必要な最小限の本番コードだけを書く。まだ必要でない機能や抽象化は追加しない。
3. **Refactor** — テストが通ったまま、重複・命名・構造を改善する。振る舞いは変えない。
4. 次の振る舞いへ進み、短いサイクルを繰り返す。

## 状況別の開始点

- **新機能**: まだ存在しない振る舞いを、最小の入力・結果でRedにする。
- **バグ修正**: まず利用者が観測する不具合を再現する回帰テストを書き、既存実装の欠陥による失敗を確認する。
- **レガシーコード・仕様不明**: 公開境界の現在の振る舞いをCharacterization Testで固定する。誤った振る舞いは、期待する仕様のRedテストへ置き換えてから修正する。
- **外部I/O・時刻・乱数・非同期**: 先に境界を決め、テストでは決定性を注入する。待ち時間や実サービスへの依存でRed/Greenを作らない。
- **テストが書きにくい**: モックを増やす前に、公開インターフェースと依存境界を見直す。設計を整えた後、最小のRedへ戻る。

## 実行ルール

- **テストファースト**。本番コードより先にテストを書く。
- **小さなサイクル**。要件を一度に実装せず、ひとつの例を通す垂直スライスで進める。
- **振る舞いをテストする**。公開インターフェースを通じて、利用者が観測できる結果を検証する。実装詳細・private メソッド・内部呼び出し回数には結びつけない。
- **テストを設計の対話相手にする**。テストが書きにくい、実行しにくい、名前を付けにくい場合は、設計やインターフェースを見直す。
- **失敗を確認する**。新しい期待振る舞いのRedが最初から通るなら、未実装の振る舞いを表せていないか、既存動作を確認しているだけかを判定する。Characterization Testの通過は問題ではない。
- **Green 前に整理しない**。リファクタリングは Green の後に行い、各変更後もテストを実行する。
- **モックは必要な境界だけ**に使い、モック自体の呼び出しではなく観測可能な振る舞いを検証する。

## ガードレール

- **NEVER** 先に複数のテストや抽象化を作る。最小の一例をRedにし、その失敗原因を確認してから次へ進む。
- **NEVER** 新しい期待振る舞いのRedが最初から通ることをRedとみなす。未実装の振る舞いを表すか、既存動作を確認しているだけかを判定する。Characterization Testは現在の動作を記録するため、通過してよい。
- **NEVER** 仮実装を最終設計とみなす。一例を通した後、異なる例で三角測量し、一般化が必要になった時点で実装を広げる。
- **NEVER** privateメソッド、内部アルゴリズム、モックの呼び出し回数を契約として固定する。公開境界の結果を検証し、リファクタリングの余地を残す。
- **NEVER** `sleep`、実サービス、実時刻だけで非同期・外部I/OのGreenを作る。決定性を注入し、待機ではなく結果と状態を観測する。

## Developer Testing

TDD のテストは、完成後の品質担保だけを目的とするテストとは役割が異なる。

- 品質担保のテスト: バグやセキュリティ上の問題を検証し、信頼性を上げる。
- **Developer Testing**: 開発者とチームに短いフィードバックを返し、次に実装すべきことを明確にする。

大きな問題を小さな振る舞いへ分解し、各サイクルの失敗と成功を開発の前進に使う。

## 完了条件

- 新しい期待振る舞いのRedは未実装の振る舞いで失敗し、バグ修正の回帰テストは既存欠陥で失敗することを確認した。
- Characterization Testの通過を失敗扱いせず、Greenでは最短の実装に留めた。
- Refactor 後もテストが通り、公開される振る舞いが変わっていない。
- 次の振る舞いが、曖昧さなく選べる状態になった。
