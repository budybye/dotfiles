# TDD（テスト駆動開発）

t-wada（和田卓人）さんの考え方に基づく、テスト設計・実装の指針。目標は「動作するきれいなコード」。動作ときれいさを同時に追わず、順番に進める。

## 基本サイクル

Red（最小の失敗テスト）→ Green（テストを通す最小限の実装）→ Refactor（振る舞いを変えない改善）を、ひとつの例ずつ短いサイクルで繰り返す。

## 状況別の開始点

- **新機能**: まだ存在しない振る舞いを、最小の入力・結果でRedにする。
- **バグ修正**: まず利用者が観測する不具合を再現する回帰テストを書き、既存実装の欠陥による失敗を確認する。
- **レガシーコード・仕様不明**: 公開境界の現在の振る舞いをCharacterization Testで固定する。**MANDATORY — READ ENTIRE FILE**: 進める前に [`references/characterization.md`](references/characterization.md) を最初から最後まで読む。誤った振る舞いは、期待する仕様のRedテストへ置き換えてから修正する。
- **外部I/O・時刻・乱数・非同期**: 先に境界を決め、テストでは決定性を注入する。待ち時間や実サービスへの依存でRed/Greenを作らない。
- **テストが書きにくい**: モックを増やす前に、公開インターフェースと依存境界を見直す。設計を整えた後、最小のRedへ戻る。

`references/characterization.md` はレガシー固定と一般化の場面専用。新機能・バグ修正・外部I/Oの開始点では読まない。

## Red の失敗判定

新しいテストが最初から通ったら、書いた意図で分類する:

| 意図 | 判定 | 次の一手 |
|---|---|---|
| Characterization Test（レガシーの現状固定） | 通過が正常 | 次の振る舞いへ |
| 新しい期待振る舞い | Red として不成立 | テスト対象と実装の接続が正しいか確認し、失敗する形に書き直す |
| 既存動作の確認 | Red ではない | 期待との差分を特定し、期待する振る舞いのテストに書き直す |

## 実行ルール

- **テストファースト**。本番コードより先にテストを書く。先に書けば仕様が先に決まり、実装の都合で振る舞いが曲がらない。
- **小さなサイクル**。要件を一度に実装せず、ひとつの例を通す垂直スライスで進める。大きな実装は失敗の候補を増やし、フィードバックを遅らせる。
- **振る舞いをテストする**。公開インターフェースを通じて、利用者が観測できる結果を検証する。実装詳細・private メソッド・内部呼び出し回数には結びつけない。内部に結びついたテストは Refactor で壊れ、振る舞いの回帰を見逃す。
- **テストを設計の対話相手にする**。テストが書きにくい、実行しにくい、名前を付けにくい場合は、設計やインターフェースを見直す。書きにくさは設計の臭いであり、モックや特殊な仕掛けで無理に通すと設計問題を固定する。
- **Green 前に整理しない**。リファクタリングは Green の後に行い、各変更後もテストを実行する。整理を先にやると失敗の原因と修正の効果が混ざり、Red の意味が曖昧になる。
- **モックは必要な境界だけ**に使い、モック自体の呼び出しではなく観測可能な振る舞いを検証する。モックの検証が目的になると、テストが通っても振る舞いが壊れている状態を見逃す。

## ガードレール

- **NEVER** 先に複数のテストや抽象化を作る。最小の一例をRedにし、その失敗原因を確認してから次へ進む。
- **NEVER** 新しい期待振る舞いのRedが最初から通ることをRedとみなす。「Red の失敗判定」の表で分類する（Characterization Test の通過は正当）。
- **NEVER** 仮実装を最終設計とみなす。一般化する前に [`references/characterization.md`](references/characterization.md) の三角測量節を読む。一例を通した後、異なる例で三角測量し、一般化が必要になった時点で実装を広げる。
- **NEVER** privateメソッド、内部アルゴリズム、モックの呼び出し回数を契約として固定する。公開境界の結果を検証し、リファクタリングの余地を残す。
- **NEVER** `sleep`、実サービス、実時刻だけで非同期・外部I/OのGreenを作る。決定性を注入し、待機ではなく結果と状態を観測する。

## Developer Testing

TDD のテストは、完成後の品質担保だけを目的とするテストとは役割が異なる。

- 品質担保のテスト: バグやセキュリティ上の問題を検証し、信頼性を上げる。
- **Developer Testing**: 開発者とチームに短いフィードバックを返し、次に実装すべきことを明確にする。

大きな問題を小さな振る舞いへ分解し、各サイクルの失敗と成功を開発の前進に使う。

## 完了条件

- 新しい期待振る舞いのRedは未実装の振る舞いで失敗し、バグ修正の回帰テストは既存欠陥で失敗することを確認した。
- Characterization Testの通過を失敗扱いせず、Greenでは最短の実装に留めた。
- Refactor 後もテストが通り、公開される振る舞いが変わっていない。
- 次の振る舞いが、曖昧さなく選べる状態になった。
